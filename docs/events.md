# Invocation event profile

Ledgence accepts CloudEvents 1.0 structured JSON. The worker receives a complete invocation envelope generated by its caller. The future orchestration service will generate platform IDs; the local fixture command creates example IDs for development.

```json
{
  "specversion": "1.0",
  "id": "evt_invocation_001",
  "source": "urn:ledgence:orchestrator",
  "type": "com.ledgence.task.invocation.requested.v1",
  "subject": "tasks/task_invoice_1042",
  "time": "2026-09-12T14:00:00Z",
  "datacontenttype": "application/json",
  "traceparent": "00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01",
  "ldgtenantid": "tenant_acme",
  "ldgnamespace": "billing",
  "ldgrunid": "run_order_1042",
  "ldgtaskid": "task_invoice_1042",
  "ldgattemptid": "att_invoice_1042_01",
  "ldgattemptno": 1,
  "data": {
    "invoice_id": "INV-1042",
    "order_id": "ORD-1042"
  }
}
```

`data` is entirely application-owned. It may be any JSON value. Ledgence does not inject execution metadata or prescribe a business-ID hierarchy inside it. Preservation means logical JSON values within the current parser's numeric precision, not byte-for-byte whitespace or key ordering. Rust uses signed/unsigned 64-bit integers and binary64 floating point; Python uses binary floating point for JSON fractions. Larger integers may be rounded during parsing, and out-of-range numbers are rejected. Encode exact decimal amounts or identifiers exceeding that range as strings. Arbitrary-precision number support is not implemented.

| Field | Meaning and stability |
| --- | --- |
| `source` + `id` | Identity of this event; redelivery of the same event preserves both |
| `ldgrunid` | Orchestration run grouping related tasks |
| `ldgtaskid` | Logical task identity, retained across its attempts |
| `ldgattemptid` | One execution attempt; a new attempt needs a new ID |
| `ldgattemptno` | Positive signed 32-bit attempt number |
| `ldgtenantid`, `ldgnamespace` | Execution ownership and grouping |
| `traceparent` | Propagated W3C trace context, independent of event and business identity |

The profile requires `specversion`, `id`, `source`, `type`, `datacontenttype: application/json`, all six `ldg` fields shown above, and `data`. `subject`, `time`, `dataschema`, `traceparent`, and `tracestate` are optional and validated when present. This version accepts W3C `traceparent` version `00`; `tracestate` requires `traceparent`. The profile does not support `data_base64`. Context attributes use lowercase alphanumeric names and CloudEvents scalar types; optional attributes must be omitted instead of set to null.

Trace IDs do not replace task IDs, idempotency keys, or business IDs. The worker passes tracing attributes through and includes trace context in invocation logs; it does not yet create OpenTelemetry spans or automatically instrument the user's application. No additional request/parent-ID convention is standardized in this milestone.

The worker rejects simultaneous ownership of one tenant/namespace/attempt identity locally. This is not durable deduplication. A future delivery adapter must define redelivery, leases, and settlement, and preserve the logical task's immutable program descriptor across retries. Programs remain responsible for idempotent business effects.
