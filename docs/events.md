# Invocation event profile

Ledgence accepts CloudEvents 1.0 structured JSON. The worker receives a complete invocation envelope generated by its caller. The Rust orchestration service and PostgreSQL adapter generate and persist platform identities and invocation events; the [HTTP delivery path](http-orchestration.md) transports them to connected workers. The local fixture command creates example IDs for development.

```json
{
  "specversion": "1.0",
  "id": "evt_invocation_001",
  "source": "urn:ledgence:orchestrator",
  "type": "com.ledgence.task.invocation.requested.v1",
  "subject": "tasks/task_invoice_1042",
  "time": "2026-09-12T14:00:00Z",
  "datacontenttype": "application/json",
  "traceparent": "00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01",
  "ldgtenantid": "tenant_acme",
  "ldgnamespace": "billing",
  "ldgrunid": "run_order_1042",
  "ldgtaskid": "task_invoice_1042",
  "ldgattemptid": "att_invoice_1042_01",
  "ldgattemptno": 1,
  "data": {
    "invoice_id": "INV-1042",
    "order_id": "ORD-1042"
  }
}
```

`data` is entirely application-owned. It may be any JSON value. Ledgence does not inject execution metadata or prescribe a business-ID hierarchy inside it. Preservation means logical JSON values within the current parser's numeric precision, not byte-for-byte whitespace or key ordering. Integer tokens must fit from `-2^63` through `2^64 - 1`. The CLI rejects larger integer tokens before parsing or execution. Fractions and exponent-form numbers use finite binary64 floating point; decimal text is not an arbitrary-precision decimal representation. Binary64 round-trip parsing is enabled so supported Python floats retain their value across the protocol. Encode exact decimal amounts or identifiers exceeding that range as strings. Arbitrary-precision number support is not implemented.

| Field | Meaning and stability |
| --- | --- |
| `source` + `id` | Identity of this event; redelivery of the same event preserves both |
| `ldgrunid` | Orchestration run grouping related tasks |
| `ldgtaskid` | Logical task identity, retained across its attempts |
| `ldgattemptid` | One execution attempt; a new attempt needs a new ID |
| `ldgattemptno` | Positive signed 32-bit attempt number |
| `ldgtenantid`, `ldgnamespace` | Execution ownership and grouping |
| `traceparent` | Propagated W3C trace context, independent of event and business identity |

The profile requires `specversion`, `id`, `source`, `type`, `datacontenttype: application/json`, all six `ldg` fields shown above, and `data`. `subject`, `time`, `dataschema`, `traceparent`, and `tracestate` are optional and validated when present. This version accepts W3C `traceparent` version `00`; `tracestate` requires `traceparent`. The profile does not support `data_base64`. Context attributes use lowercase alphanumeric names and CloudEvents scalar types; optional attributes must be omitted instead of set to null.

Trace IDs do not replace task IDs, idempotency keys, or business IDs. The event carries its immutable creation context. Optional [OpenTelemetry instrumentation](observability.md) creates separate producer, processing, and execution spans, while HTTP request IDs remain per-exchange diagnostics. Python protocol v2 receives active execution context separately; user data is untouched. Application instrumentation remains explicit.

The worker rejects simultaneous ownership of one tenant/namespace/attempt identity locally. This is not durable deduplication. The [delivery contract](delivery-contract.md) defines redelivery, leases, and settlement; the [PostgreSQL adapter](postgres.md) persists those records and the logical task's immutable program descriptor across retries. The HTTP adapter connects these operations to worker execution. Programs remain responsible for idempotent business effects.

Transport adapters should use `ledgence_worker_api::decode_json` before constructing a `CloudEvent`; constructing one from an already-rounded `serde_json::Value` cannot recover the original token. The helper rejects out-of-range integer tokens without inspecting strings or reserving application keys.

Success and failure reports include `source`, `event_id`, `tenant_id`, `namespace`, `run_id`, `task_id`, `attempt_id`, `attempt_no`, bound `program` and `digest`, and optional `traceparent`/`tracestate`. These are copies of the envelope and binding, not fields injected into `data`. A failure retains its primary error and a separate `cleanup_error` if cleanup also failed.

Program results follow the same numeric range, require string object keys and Unicode scalar strings, and allow at most 64 nested arrays/objects. Unsupported Python results become typed `invalid_output` failures without terminating an otherwise healthy process. See the [Python helper contract](../sdk/python/README.md).

## Workflow identity

Workflow activation and child task events additionally contain `ldgworkflowid`, identifying their workflow execution. Controller events also contain `ldgactivationid`, equal to their stable controller task ID across attempts. Existing `ldgrunid` remains the per-task run identity; workflow support does not reinterpret it. These optional identifiers remain outside application-owned `data` and propagate into execution reports and tracing. Checkpoint state and local journals use the separate [workflow runtime context](workflows.md).
