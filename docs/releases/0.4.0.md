# Ledgence 0.4.0

Ledgence 0.4.0 simplifies CLI installation and local startup with a verified
installer, persistent Docker Compose installations and versioned container
images. Existing source builds and manual deployment remain available.

The [0.4.0 release](https://github.com/Ledgence/ledgence/releases/tag/v0.4.0)
includes native bundles, container images, the installer, the local deployment
kit and matching Python/Rust registry packages.

## Install the CLI and configure your shell

The new installer selects the supported native bundle, verifies its archive and
internal checksums, and checks the executable before activating it. It installs
without sudo, retains the complete bundle and legal notices, and preserves the
previous selection if downloading or verification fails.

Install this release:

```sh
curl --proto '=https' --tlsv1.2 -sSfL https://github.com/Ledgence/ledgence/releases/download/v0.4.0/install.sh | sh -s -- --version 0.4.0
```

Supported shell startup files are configured for future terminals. To activate
the default installation in the current Bash, Zsh or POSIX shell:

```sh
. "$HOME/.local/share/ledgence/env"
ledgence --version
```

A piped installer cannot change its parent shell's environment. Custom prefixes
and `--no-modify-path` are available. The installed CLI also discovers its bundled
Python worker helper and, with explicit instance configuration, its Console
assets; explicit resource paths still take precedence.

See [installation and shell setup](../installation.md).

## Run and manage a persistent local stack

A complete 0.4.0 native bundle includes a matching, digest-pinned deployment kit.
With Docker running Linux containers and Compose 2.23.1 or newer:

```sh
ledgence local up
ledgence local status
ledgence local logs --service worker --tail 50
ledgence local down
```

The stack starts PostgreSQL, migration, the orchestrator with Console, and one
worker. It pulls prebuilt images and requires no checkout, Rust, Node or host
Python installation. The CLI waits for readiness and prints the API and Console
addresses; Console normally opens at `http://127.0.0.1:8080/console/`.

`down` preserves named volumes and saved configuration. Subsequent `up` reuses
the project's image, Docker context, port and concurrency. Installing a newer
CLI does not silently upgrade that project. The base stack starts without
application programs; optional Compose examples add real tasks, workflows and
completion callbacks. Direct Compose use remains supported.

See [the local distribution](../container-distribution.md) and
[optional examples](../installation.md#run-the-optional-container-examples),
including the separate project lifecycle when switching to direct Compose.

## Distribution and upgrade scope

| Distribution | Targets |
| --- | --- |
| Native CLI with Console | Linux x86_64/glibc (Ubuntu 24.04 qualification target); macOS arm64 |
| Container runtime with CPython 3.14 | Linux amd64 and arm64, with native-runner qualification for each |
| Python client | Python 3.11–3.14 on the reviewed Linux x86_64/glibc and macOS arm64 matrix |

Container architecture support does not add native Linux arm64, Windows or macOS
Intel executables. Program packages must still match the worker's platform and
exact Python major/minor; one application package does not become portable
across architectures because the runtime image supports both.

There are **no new PostgreSQL migrations relative to 0.3.1**. Console contract
**5**, workflow runtime protocol **3**, and the `ledgence.client` /
`ledgence.worker` namespaces remain unchanged. The CLI, Console, Python client
and two Rust API crates use version 0.4.0.

The published 0.3.1 bundles contain neither `ledgence local` nor a deployment kit.
A new local installation is separate from an existing source-Compose deployment;
it does not import that deployment's volumes. Keep the existing deployment and
its data until an explicit migration has been planned. Installing the CLI does
not upgrade running services or saved local projects.

## Qualification and maintenance

CI separates PostgreSQL, HTTP, SQS and workflow acceptance into independent jobs
while preserving the existing scenarios and OS/Python coverage. Acceptance suites
reuse executables built for that workflow run, verify their source identity and
checksums, and retain evidence and timing records. Real lease-expiry and
production long-poll coverage remain in place. Package publication still requires
the full source checks for the selected release commit.

Python client deadline regression tests now control the boundary under test,
reducing dependence on runner scheduling without relaxing timeout assertions.
Documentation adds a capability map and refreshes installation, workflow,
observability, SDK and example guidance.

Container publication retains SBOMs, provenance, notices and corresponding
third-party sources, and verifies the transferred artifacts before publication.
Ledgence-owned code remains MIT; third-party components retain their own licenses.
This release does not extend the documented trusted-code boundary or make new
production-capacity guarantees.
