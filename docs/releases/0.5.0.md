# Ledgence 0.5.0

**Release preparation: qualification and publication are in progress.** These
notes describe the source selected for 0.5.0, compared with the stable 0.4.0
release. They do not confirm registry packages, native bundles or container image
availability. Version 0.4.0 remains the latest stable release; 0.4.1 remains a
prerelease while this release is prepared.

Ledgence 0.5.0 adds explicit Python program preparation and remote publication
through the unified CLI, with saved receipts for recovery. It also packages the
existing `ledgence.worker` authoring helpers for installation in a developer's
Python environment. Existing filesystem publication and manual preparation stay
available.

## Prepare a program for its worker

`ledgence program build` reads `ledgence.toml`, selects application files and
prepares dependencies for an explicit Linux worker target. A local Docker adapter
uses the configured digest-pinned runtime image; the build verifies the target's
OS, architecture and exact CPython major/minor. The CLI does not infer the target
from the developer's machine or a connected worker.

Requirements must include exact versions, SHA-256 hashes and all active
transitive dependencies. This adapter installs compatible wheels from public
PyPI with hash checking; it does not compile source distributions or support
private indexes and editable dependencies. Applications with other preparation
needs can continue to supply an already prepared directory. Dependency license
notices remain part of the application package.

A completed build returns the prepared directory, immutable artifact descriptor
and a build receipt containing input/output hashes, target and image identity.
Existing outputs are never overwritten. No build, publication or registration
step imports or executes the application handler.

See [build configuration and limits](../program-publication.md#explicit-build-configuration)
and the [HTML report workflow example](../../examples/program-publication/README.md),
which uses a native Python dependency in the worker runtime.

## Publish remotely and recover an interrupted operation

With a compatible CLI and an installation explicitly configured to accept
program uploads, the default prepared directory can be published and registered:

```sh
ledgence program build
ledgence program publish --server http://127.0.0.1:8080 --register
```

Build, publication and catalog registration are separate operations. Publication
validates and stores the immutable ZIP. Optional registration records its
verified descriptor and descriptive metadata in the installation's catalog;
it does not start a task or workflow.

Before sending the archive, the CLI retains its exact ZIP and publication
receipt. An uncertain upload can be reconciled with those same bytes:

```sh
ledgence program publish --resume /absolute/path/to/receipt.json
```

Resume verifies the saved artifact and retries only unconfirmed stages. If upload
was confirmed but catalog registration failed, it retries registration without
uploading again. It does not rebuild from a changed project. A timeout means the
publication outcome may be unknown; it does not establish rollback. Keep the
receipt and its sibling archive together. The initial upload makes one PUT,
without automatic retries.

The HTTP API adds publication capability discovery and a bounded binary upload
route. Identical publication is idempotent. Different bytes for an existing
`(program_id, version)` return an immutable conflict. This identity is global
within the store, even when catalog records use different tenant/namespace
values. A build for another architecture therefore needs a different ID or
version; this release does not add multiarchitecture variants under one program
version.

See [publication, registration and recovery](../program-publication.md#publish-register-and-recover)
for result fields, bounds and error semantics. Custom storage adapters can
implement the new `ProgramArtifactPublisher` write port independently of the
worker's `ProgramStore` reader and `ArtifactCache`.

## Install Python authoring helpers

The separately packaged `ledgence-worker` distribution provides
`from ledgence.worker.workflow import Workflow` and the existing invocation,
logging and workflow helpers for editors and local application tests. It has no
runtime dependencies, requires Python 3.11 or newer, includes typing metadata,
and shares the `ledgence` namespace with `ledgence-client`.

Use it as a development dependency matching the deployed worker. It is not a CLI,
service or standalone workflow execution harness. At execution, the Rust worker
still supplies its matching helper. Application runtime dependencies must be
prepared for the worker separately; do not vendor `ledgence-worker` as one of
those dependencies.

Registry publication is still pending for 0.5.0. Until verified, use the
[source installation instructions](../../sdk/python/README.md#install-from-source).
The worker package, client and Rust API crates are qualified and published through
the [registry workflow](../registry-packages.md), including installation outside
the checkout and checks that both Python distributions coexist.

## Upgrade and operating scope

- Program upload is disabled by default. Self-hosted operators enable
  `--allow-program-publication` with an instance configuration and writable
  filesystem store. The supplied updated Compose templates enable that writer
  explicitly, give the orchestrator write access and keep worker mounts read-only.
  An HTTPS read-only store cannot enable this filesystem writer.
- Upload requires a matching updated CLI and server. Installing a new CLI does
  not upgrade running services, overwrite a saved local kit or enable upload in
  an older installation. Evaluate a new qualified kit in a separate state
  directory, or plan an explicit upgrade with backups.
- Build targets are Linux amd64 or arm64. Use the same digest-pinned image as the
  worker and qualify actual native imports there. A compatible architecture and
  Python version alone do not prove compatible system libraries. Building needs
  a local Docker endpoint; publishing a prepared package and running it do not
  require Docker access on the orchestrator or worker.
- Workers on separate hosts still need access to the same artifacts through the
  existing filesystem or HTTPS reader. Upload does not configure replication,
  object-storage distribution or credentials.
- There are no new PostgreSQL migrations relative to 0.4.0. Console contract 5 and
  workflow runtime protocol 3 remain unchanged. Rust adapters constructing
  `RegisterProgram` directly must set the new `expected_descriptor` field to
  `None` or the descriptor they intend to register; the HTTP JSON field is optional.

The planned native distribution remains Linux x86_64/glibc and macOS arm64, with
Linux amd64/arm64 container runtimes using CPython 3.14. Support for a container
architecture does not add a native executable target. Only artifacts that finish
qualification and public download verification belong in the final release.

## Qualification

Release qualification is in progress for the selected 0.5.0 source. Tests cover
immutable publication across processes, interrupted writes, archive validation,
upload admission through timeout and disconnect, receipt recovery and exact
catalog descriptor binding. The local distribution acceptance gate prepares the
native-dependency example twice, compares descriptors, publishes and registers it,
executes it in the target worker, restarts the stack and verifies persistence and
another execution. These scenarios must pass for the release's actual images and
bundles; the presence of tests is not a completed qualification result.

This change preserves the operator-trusted-code boundary, existing delivery and
external-effect semantics, and framework independence. Ledgence-owned code
remains MIT; third-party licenses and required notices still apply. See the
[release procedure](../releasing.md) for evidence and publication ordering.
