# Ledgence 0.6.0

Ledgence 0.6.0 adds functional Python project scaffolding and improves program
build cleanup and Console execution inspection. These notes compare the release
source with 0.5.0.

The [0.6.0 release](https://github.com/Ledgence/ledgence/releases/tag/v0.6.0)
includes matching native bundles, Console, installer, local kit, Linux container
runtimes, Python client and worker helper packages, and Rust API crates. Required
qualification and public download checks completed on **2026-10-20**.
Website deployment is a separate operation.

## Create a working Python project

The unified CLI creates a task by default or an enum-based workflow:

```sh
ledgence program new invoice-issuer
ledgence program new invoice-flow --kind workflow
```

Each project includes a functional greeting handler, standard-library tests,
`pyproject.toml`, `ledgence.toml`, `requirements.txt`, `.gitignore` and a README.
Both starters accept `data={"name": "Ada"}` and produce
`{"message": "Hello, Ada!"}` when executed. The workflow registers a typed default
entrypoint and completes through its workflow context.

Scaffolding works offline and does not run Python, a package manager, Git, Docker
or a service. The destination must not exist and its parent must already exist.
Existing files and directories are never overwritten.

The generated uv application project pins both `ledgence-worker` and
`ledgence-client` as development dependencies to the generating CLI's version.
The helper supports program authoring, editor imports and local business-logic
tests. `from ledgence.client import AsyncClient` supports submission and
inspection against a running service. Install the matching published packages
and run the generated tests with:

```sh
cd invoice-issuer
uv sync
uv run python -m unittest discover -s tests -v
```

These tests check the starter's business logic and handler or workflow
registration; they do not simulate durable orchestration. Application runtime
dependencies remain separate build requirements. The deployed Rust worker still
supplies its own Python helper.

Before building, choose the worker's Linux platform, exact CPython major/minor
and digest-pinned image in `ledgence.toml`, or supply all three target options at
creation. A laptop's architecture is not selected implicitly. Building,
publication, registration and execution remain explicit steps. See the
[CLI scaffolding contract](../cli.md#create-a-python-program) and
[program preparation and publication](../program-publication.md).

## Program creation and test fixtures

Program creation is consolidated on `ledgence program new`; the legacy
program-fixture generator has been removed. The new command creates application
source, not a prepared native package or a local worker task file. Existing
scripts using generated fixtures must prepare their package and invocation
fixture explicitly, using the [package contract](../program-packages.md), or
adopt the new-project build and publication flow.

Repository acceptance tests, release smoke checks and local Compose preparation
now create their fixtures directly. Published programs retain their immutable
identities and artifacts; this CLI change does not rewrite them.

## Fixes

- The locked TLS dependency Rustls is updated to `0.23.46` and the archive
  dependency ZIP to `9.0.5` to address upstream advisories found by the release
  dependency gate. Existing dependency policy and artifact bounds remain in
  force; see the [dependency review](../dependencies.md#release-06-tls-and-archive-dependency-update).
- Cancelling a Docker program build while its container ID file is still empty
  now looks up the invocation's owned container before cleanup. It continues to
  reject malformed or ambiguous identifiers rather than removing an unrelated
  container.
- Console local checkpoints refresh while a workflow is active and receive a
  final refresh when it becomes terminal. The selected activation remains bound
  to its URL and pagination even when another entrypoint starts; copied links
  retain that selection.
- Trace views measure the visible viewport so tall or resized panels display
  the rows that fit, while retaining bounded virtualization and follow behavior.
- The workflow Input panel accurately describes the original submitted input.
- PostgreSQL regression coverage exercises both orderings of an owned approval
  resumption and root-workflow cancellation, including accepted-decision replay
  and the absence of newly claimable work after cancellation.

## Validation tooling

The HTTP acceptance harness binds its artifact listener before selecting the API
port, preventing the fixture from reclaiming that port and answering an API
readiness check with the wrong service. The Console terminal-checkpoint
regression waits for rendered state and deliberately delays query notifications
to verify the final refresh without depending on scheduling speed. These are
validation improvements, not changes to production listener or retry behavior.

## Upgrade and operating scope

There are no new PostgreSQL migrations relative to 0.5.0. Console contract **5**,
workflow runtime protocol **3**, and the existing public Rust and Python API
contracts remain unchanged. Keep CLI, services, Console assets and Python helpers
at matching release versions and retain normal backups and upgrade checks.

Installing a new CLI does not upgrade a saved local installation, replace its
pinned image or enable a server writer. Evaluate a matching qualified local kit
in a separate state directory, or perform an explicit service upgrade. Existing
program identities and versions remain independent of the platform version.

The qualified distribution targets are Linux x86_64/glibc and macOS arm64
native bundles, with Linux amd64/arm64 container runtimes. A supported container
architecture does not imply a native executable bundle for that architecture.

This release preserves the operator-trusted-code boundary, existing delivery
and external-effect semantics, and framework independence. Ledgence-owned code
remains MIT; third-party components retain their licenses and required notices.
See the [release procedure](../releasing.md) for qualification, provenance and
publication ordering.
