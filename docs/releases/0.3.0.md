# Ledgence 0.3.0

Ledgence 0.3.0 adds durable human approvals, recovery for model and tool calls,
and an optional MCP server. The platform remains framework-agnostic: provider
clients, tool discovery and agent frameworks belong to application code or
optional adapters. Self-hosting requires no model provider account.

Read the [upgrade guide](../upgrading-to-0.3.md) before replacing 0.2 services.
This release adds a PostgreSQL migration and requires Console contract **5**.

## Review the exact action before execution

Workflows can save an immutable action and release their worker slot while a
person reviews it. Approval decisions bind to the persisted request, effective
arguments and deadline. The Python helper runs the saved arguments; approval
cannot silently substitute a new action. Console's **General → Approvals**, the
Python client and `ledgence approval` provide review and decision operations.

Lost decision replies are reconciled with the same prepared command. Rejection,
expiry and cancellation remain explicit outcomes. These guarantees bind Ledgence's
invocation; external effects still require application idempotency or reconciliation.
See [durable approvals](../workflow-approvals.md).

## Recover dynamic agent operations

`ctx.operation` persists a completed model or tool result using an explicit
operation key and immutable callable/input binding. Retrying the same activation
reuses a committed result; a changed binding is rejected before the changed call
runs. Applications can discover tools dynamically and checkpoint their own loop
state without putting a provider SDK into Ledgence's core.

This is not Python stack restoration or token-stream resumption. A provider call
can repeat if it succeeded before its local result was durably acknowledged.
See [operation recovery](../agent-recovery.md) for keys, limits and uncertainty.

## Connect through MCP

`ledgence mcp serve` exposes 15 tools over stdio for program discovery, task and
workflow submission, status/results, cancellation, workflow events and approval
inspection. It connects to the existing HTTP API with a fixed tenant/namespace;
`--read-only` exposes only observation tools. Submission returns a durable identity
without waiting for the entire execution.

MCP request cancellation or disconnection does not cancel durable work.
Interrupted submissions can be reconciled with their original idempotency key
and input. The optional adapter uses portable service contracts and the official
Rust MCP SDK. It does not expose approval decisions, model sampling or Streamable
HTTP. See [MCP setup](../mcp.md).

## Reliability and quality corrections

- PostgreSQL and workflow control exchanges account for synchronous work within
  their deadlines and preserve uncertain-outcome reconciliation.
- Task HTTP responses are checked against the requested execution and submission;
  structurally valid data from a different task is rejected.
- A late Console submission response no longer redirects a user who left its form.
  Obsolete list components have been removed.
- The local webhook example rejects conflicting source/ID duplicates and reports
  storage failures as retryable. Identical redelivery stays idempotent.
- Disposable acceptance databases are cleaned after uncertain creation replies.
  Rust package qualification supports optional private adapters while publishing
  only the two API crates.
- Local image builds revalidate copied dependency patches offline, and native
  checksum instructions work with older system Python installations.

The examples include durable approvals, agent recovery, a fulfillment-incident
investigation, and an expanded Codex change-review workflow. Their offline modes
exercise real orchestration without model requests. Application package versions
remain independent of the Ledgence platform version.

## Distribution and compatibility

The unified CLI, Python client and Rust API crates use **0.3.0**. Console-enabled
native bundles target **Linux x86_64/glibc** (Ubuntu 24.04 qualification) and
**macOS arm64**. The supported Python matrix remains **3.11–3.14**. CPython,
PostgreSQL, brokers and host libraries are supplied separately; archive provenance
records actual library requirements.

Upgrade worker, runtime helper, orchestrator, client and Console together. Apply
migrations explicitly with old writers stopped; mixed Console contracts are
unsupported. Custom Rust adapters must account for the new approval-related enum
variants and service operations. Workflow runtime protocol **3**, the
`ledgence.client` / `ledgence.worker` namespaces, immutable programs and existing
execution identities remain in use.
