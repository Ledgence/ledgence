---
title: Recover an asynchronous provider operation
description: Approve a frozen provider request, dispatch once and release the worker between bounded status checks.
---

Available in Ledgence 0.9.0 with matching components, credentials and an explicit
provider policy.

An export service might accept a request immediately and produce its file minutes
later. If the response is lost, sending the request again may create another
export. A provider adapter gives Ledgence separate callbacks for dispatch and
read-only status checks, plus an explicit definition of completion.

## Start with the runnable example

The provider-recovery example creates a real CSV file through a local HTTP
service. It includes a workflow, approval, two single-slot workers and a separate
queue for status checks. Its provider records requests independently so the
checks can distinguish repeated network requests from repeated effects.
[Provider-recovery example](https://github.com/Ledgence/ledgence/tree/develop/examples/provider-recovery).

Use the example's `program.py` as the starting point in your editor. Keep the
adapter and its workflow in the same prepared package. The worker retrieves that
immutable package through the normal program store and cache.

## Bind the intent before approval

Register a `ProviderAdapter` and pass it to `Workflow(Entry, providers=[adapter])`.
Decorate one function with `@adapter.dispatch` and a separate read-only function
with `@adapter.probe`. `workflow.build()` freezes those registrations. The
callbacks receive a `ProviderRequest` with independent copies of its approved
`arguments`, `binding`, `target` and optional `provider_reference`.

Create the binding in the requesting entrypoint. It contains these distinct
identities and operating limits.

| Binding field | What the application supplies |
| --- | --- |
| `business` | A namespace and stable key for the logical business operation. |
| `target` | Provider, environment, account, API variant, operation, endpoint identity and relevant dimensions. |
| `deduplication` | The provider's actual deduplication domain, key and known validity horizon, or `None`. |
| `credential_reference` | A configuration reference resolved by the application adapter. |
| `reconciliation` | A dedicated queue, timing, check budget and absolute elapsed-time budget. |
| `contract` | The registered callback identities, adapter version, contract digest and completion criterion, generated by the helper. |

Disable transparent retries and redirects in the dispatch callback’s HTTP client
when one network attempt is required.

The effective request appears once in `action.arguments`. The backend attaches
the actual immutable program descriptor before the operator can inspect or
approve the request. Approval binds that complete intent. A changed target,
request, key, adapter or policy requires a new review.

The business identity is unique inside the installation scope. An equal existing
binding returns its original ticket. A conflicting binding fails. An occurrence
owned by another workflow remains owned by that workflow.

## Dispatch and park

The requesting entrypoint returns `ctx.request_provider_approval(...)`. In its
resume entrypoint, check approval before invoking the registered dispatch.
The following excerpt uses the `Entry` enum from the example.

```python
from ledgence.worker.providers import ProviderSelectionKind
from ledgence.worker.workflow import ApprovalStatus

@workflow.entrypoint(Entry.DISPATCH)
async def dispatch(event, ctx):
    if ctx.approval.status is not ApprovalStatus.APPROVED:
        return ctx.complete({"status": ctx.approval.status.value})

    # This always returns an identity that can be inspected later.
    ticket = await ctx.approved_provider_operation()
    if ticket.occurrence.workflow_id != ctx.workflow_id:
        return ctx.complete({"existing_operation": ticket.to_dict()})

    # Returning this checkpoint releases the worker for other work.
    return ctx.wait_provider_operation(
        "export-result", ticket=ticket, resume=Entry.COMPLETE, state={}
    )

@workflow.entrypoint(Entry.COMPLETE)
async def complete(event, ctx):
    outcome = ctx.provider_operation_result
    if outcome.kind is ProviderSelectionKind.PROVIDER_SUCCEEDED:
        return ctx.complete(outcome.result)

    if outcome.kind in (
        ProviderSelectionKind.NEEDS_REVIEW,
        ProviderSelectionKind.DISPUTED,
    ):
        # The revision keeps this follow-up wait stable across attempt retries.
        # Its default threshold waits for newer evidence or an assessment.
        return ctx.wait_provider_operation(
            f"operator-review:{ctx.revision}",
            resume=Entry.COMPLETE,
            state={},
        )

    return ctx.complete({"status": outcome.kind.value, "selection": outcome.selection})
```

Even an immediate terminal dispatch response crosses this checkpoint and resumes
another entrypoint. That activation contributes to execution cost and latency.
A successfully returned `None` is a valid typed success result.

## Classify provider knowledge explicitly

Callbacks return a `ProviderReport` constructed with `pending`, `unknown`,
`requires_action`, `succeeded`, `failed` or `cancelled`. Include the actual target
contacted through `target=request.target`, and the provider reference and request
ID when available. These reports retain adapter-classified provenance.

A timeout, missing lookup result, HTTP 5xx or malformed reply cannot establish a
business failure. Classify those as unknown when appropriate, or let the callback
fail. Recovery retains its finite budget. Only the original durable grant can
invoke dispatch. Ledgence never automatically resends the mutation after a lost
reply, expired deduplication key or negative lookup.

For a provider with no suitable read API, register
`ProviderLookup.UNAVAILABLE` and the dispatch callback alone. Recovery records
`needs_review` without allocating dummy probe tasks. A reference-only adapter
with no recovered provider reference also needs review.

## Configure the installation

Use matching API replicas, workers and Python helpers, with the database
migration applied and scoped instance credentials configured. Set an explicit
provider policy file using your installation's existing audience.
[Configure instance access](/how-to/configure-instance-access).

```json
{
  "v": 1,
  "audience": {
    "authority_id": "your-authority",
    "instance_id": "your-instance",
    "scope": {"tenant_id": "acme", "namespace": "billing"}
  },
  "dispatch": "enabled"
}
```

Pass that file as `--provider-config ./provider-operations.json` when starting
`ledgence orchestrator serve`, alongside the installation's instance and access
configuration. Missing provider configuration leaves this capability disabled.
An invalid audience or policy stops startup.

Run matching workers on a dedicated probe queue distinct from the controller
queue. Each worker retains one concurrency setting. A parked workflow uses no
worker slot. Each allocated probe spends one check, including a probe that fails
or loses its worker. Status checks use a 60-second task attempt with one attempt
and a separate hard callback limit of 1–30 seconds, defaulting to 10 seconds.
Preparation time and report delivery share the task attempt budget.

The default policy starts recovery after 30 seconds, allows 12 checks within one
hour, and uses a five-second initial interval bounded at five minutes. Timing
includes deterministic jitter. Configure these values to match the provider's
consistency and latency behavior. The original dispatch retains its workflow
attempt deadline.

## Inspect and resolve

Open **Effects** in Console and select a provider filter. The list exposes
knowledge, handling and the allocated-check budget. The detail view shows the
reviewed binding, current report, recovery schedule, active probe execution and
paginated immutable history. Journal acceptance remains a separate field.

When recovery needs review, inspect the actual provider state and record a
revision-bound operator assessment. Cancellation stops further scheduling and
requests cancellation of a live probe. The application remains responsible for
any external operation already started.
[Inspect and resolve effects](/how-to/inspect-effects).

A wait selects its evidence once. Later conflicting evidence remains visible
without rewriting a continuation already selected. Operator assessments retain
their own provenance and do not become provider responses.

## Restore a backup deliberately

Stop old API replicas and workers before restoring the database. Set the policy
file's `dispatch` to `declared_restore_quarantine` before restarting. This blocks
new dispatch grants, including business keys absent from the restored snapshot,
while allowing retained read-only recovery. Keep it enabled until the operator
has reconciled external operations with restored state. Ledgence requires this
explicit restore procedure to protect that boundary.
[Provider operations contract](https://github.com/Ledgence/ledgence/blob/develop/docs/provider-operations.md).

## Limit concurrent dispatch calls

Ledgence 0.9.0 can include a named resource in the provider binding
before approval. It then parks for shared capacity and consumes both permissions
atomically. A completed call may free capacity while the asynchronous business
result remains pending. Recovery probes remain outside that limit.
[Share capacity for an approved operation](/how-to/control-resource-capacity#share-capacity-for-an-approved-provider-operation).
